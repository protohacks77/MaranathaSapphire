# Offline use and caching

Build with `npm run build` and serve `dist` over HTTPS (localhost also supports service workers). Open the deployed app online once and sign in before taking the device offline. The service worker precaches the entire release: HTML, bundled JavaScript, local Tailwind CSS, report export chunks, logos, and images. A new release activates after the previous tabs close, keeping assets consistent.

Firestore uses persistent IndexedDB storage shared across tabs, without the default document cache size eviction limit. It owns the durable mutation queue and synchronizes writes when internet returns. The application does not replay a duplicate queue. Save forms finish after either server acknowledgement or a persisted local snapshot. Batches remain atomic. When durable storage is unavailable, offline saving fails visibly instead of claiming data was saved.

Lists use local snapshots and saved first-page views immediately, then apply server changes in place. Dashboard summaries, analytics, and report previews retain user-scoped IndexedDB views across reloads. Display views refresh in the background and on reconnection; after business data uploads, cached summary reads are invalidated and figures refresh. Firestore manages query resume tokens and incremental synchronization. Historical pages load explicitly. A top status notice shows the red hospital loader, completion, offline state, queued uploads, and upload errors.

Patient registration details are retained as a device draft. Offline registrations use unique `OFF-` IDs; these remain the patient's hospital number and are not automatically renumbered. Clinical notes, vitals, ordinary document changes, messaging, payments, and ordinary billing batches can be captured offline if their prerequisite data is available on the device. Server transactions (stock dispensing/editing and automatic bed billing) and Firebase Auth operations need internet. First-time pages/records cannot fetch data that has never reached the device. Cached display summaries never authorize transaction decisions.

Application view caches and pending-upload labels are scoped to the authenticated user. SDK snapshots in the extra read cache remain in memory and are cleared on account changes. The service worker only caches declared application assets, never medical API responses. Device storage survives closing the browser; clearing site data or browser eviction removes local records. Pending writes must be uploaded before deliberately clearing storage. Server permission or validation failures are shown in the top notice; review the last save if an upload is rejected.

Validation: TypeScript and production build; focused browser checks against a dummy disconnected Firebase project for set/add/batch persistence across reload, and against the local production build for complete service-worker precaching/offline startup. No hospital data was changed for these checks.
